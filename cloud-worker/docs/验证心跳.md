# 怎么证明心跳「真的在跑」——别拿 /health 骗自己

> 这份文档来自一次真实的误判：连续两天用 `/health` 判断「云端正常」，结果发现**每次查询本身就是一次唤醒**，
> 等于自己把证据造出来了。下面把三层证据的强弱讲清楚，附可直接复制的接口。

---

## 一句话结论

| 你想证明的事 | 该看哪里 | 强度 |
|---|---|---|
| 服务活着 | `/health` | ⚠️ 弱：你的访问本身就是一次唤醒 |
| **平台有没有按时发车** | 调度任务日志（列表） | ✅ 强：`triggerType` + `startTime` |
| **那次运行是不是跑在云端** | 同一条日志的 `executorNode` | ✅✅ 最强：`agentserver-*` 就是平台 pod |
| **那次跑出了什么业务结果** | 日志详情里的 `agentOutput` | ✅✅ 最强：worker 当场回的原文 |

---

## 一、为什么 `/health` 不能当证据

`/health` 返回的 `lastTickAt` 和 `tickCount` 是**单点快照**，而且：

- 沙箱是**请求驱动**的：你请求 `/health` → 沙箱被唤醒 → **启动即跑一轮** → `lastTickAt` 更新成「刚刚」。
- 于是「我刚查过，lastTickAt 是新的」永远成立，**和你关心的问题（它自己会不会按时醒）完全无关**。

> 实测记录：某次本地体检时 `tickCount` 从 45 涨到 46，而那一次正是体检本身造成的。
> `/log` 的内存环形缓冲同理——沙箱重启就清空，看到的「刚启动」不代表别人叫醒过它。

## 二、正确的判据：平台调度日志

### 1）任务定义 + 最近 N 次运行

```bash
TASK_ID=你的任务id
TOKEN=你的 access token

# 任务本身（cron、是否 ACTIVE、下次运行）
curl -s "https://www.workbuddy.cn/v2/as/scheduler/tasks/$TASK_ID" \
  -H "Authorization: Bearer $TOKEN" -H "Accept: application/json" \
  -H "Origin: https://www.workbuddy.cn" -H "x-codebuddy-request: 1" -H "x-client-platform: web"

# 最近 N 次运行
curl -s "https://www.workbuddy.cn/v2/as/scheduler/tasks/$TASK_ID/logs?page=1&page_size=10" \
  -H "Authorization: Bearer $TOKEN" ...同上
```

关键字段：

| 字段 | 含义 | 怎么判 |
|---|---|---|
| `triggerType` | `scheduled` = 到点自跑；`manual` = 手动触发 | **只看 `scheduled`** |
| `status` | `success` / 失败 | 失败要告警 |
| `startTime` | 实际开跑时间 | 与 cron 对比，看延迟是否离谱 |
| `executorNode` | 在哪台机器执行 | `agentserver-xxxx` ⇒ **平台云端**；出现你的主机名 ⇒ 跑在本机 |
| `deliveryStatus` | 结果有没有推送出去 | `success` ＝ 你手机上应该收到过 |

### 2）单次运行详情（最有说服力的一层）

```bash
curl -s "https://www.workbuddy.cn/v2/as/scheduler/tasks/$TASK_ID/logs/<logId>" \
  -H "Authorization: Bearer $TOKEN" ...同上
```

返回里有两个「原文」字段：

- `agentInput`：这次任务**实际发出的提示词**（能看出它访问的是哪个 URL）；
- `agentOutput`：agent 的回复，`data.result` 就是 worker 返回的业务战报，例如：

```
✅ 2026-10-19 09:47｜签到 2/2 全成 +200（连续 19 天） · 猫猫 10 只已跑满 · 令牌剩 27.6 天 · 正常
```

**「云端发请求 → worker 回内容 → 内容被记录」这条链闭合，就证明机器不在这条链上。**

## 三、怎么做一次「关机实测」（可选，但最直观）

1. 选一个**你一定关着电脑**的时段（例如凌晨）。
2. 在这个时段里，让心跳按 cron 跑一次（要么把 cron 调到这个点，要么另建一条一次性任务）。
3. 第二天开机后，对比两件事：
   - 调度日志里那条 `startTime` 落在关机时段内、`status=success`、`executorNode=agentserver-*`；
   - 本机 `LastBootUpTime` **晚于**那个 `startTime`。

两者对上 ⇒ **不依赖本机的结论就算落地了**，不再需要相信任何人的口头断言。

> 没做关机实测也**不影响结论**：`executorNode` 本来就是「在哪跑」的直接证据，关机实测只是让非技术读者更信服。

## 四、四种常见误判

1. **把「我访问成功」当「它自动跑了」** —— 你的访问会造出一次 tick。
2. **把 `nextRunAt` 当「跑过了」** —— 那只是排期，过期才是异常信号。
3. **把「签到已完成」当「云端签的」** —— 若 `note` 是「先前已领」，说明它检查时已经签过，**归因不了**（可能是你手动签的、也可能早一轮签的）。
4. **把「沙箱被回收」当「服务挂了」** —— 回收是正常节能行为；关键是下一次唤醒是否按 cron 发生。

## 五、配套工具

| 脚本 | 作用 | 零成本？ |
|---|---|---|
| `tools/心跳对账.cjs` | 把上面的日志翻成人话：时间线 + 自动/手动 + 执行节点 + 业务结果 + 节奏判断 | ✅ 只读接口 |
| `tools/心跳告警.cjs` | 定期体检，异常时落一份告警文件（可挂系统计划任务，建议每天一次 + 开机补跑） | ✅ 只读接口 |

```bash
node tools/心跳对账.cjs 10
node tools/心跳告警.cjs            # 退出码 0 正常 / 1 异常
node tools/心跳告警.cjs --selftest # 验证告警链路（产物带 -selftest）
```

> ⚠️ 告警脚本挂在**本机计划任务**上时，关机期间不跑（靠「错过则开机补跑」兜底）。
> 这不是缺陷而是取舍：云侧的「第一信号」是心跳自身的手机推送（`deliveryStatus`），
> 本机告警的价值是**故障域不同**——云端整套调度都挂掉时，它还能在你开机后告诉你。
