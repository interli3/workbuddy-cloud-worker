# WorkBuddy 成长任务机制详解

> 这一页解释 `growth-tasks.js` 里每条配方**为什么这么写**。想加新任务，照这里的模式抄。

---

## 一、大前提：进度 = 遥测埋点

成长任务的进度由服务端根据**客户端上报的遥测事件**统计，不校验事件是否真的对应一次真实操作。

- 上报地址：`POST https://www.workbuddy.cn/v2/report`
- 请求体：**事件数组**，每条至少包含 `eventCode`，外面包一层公共字段（`userId` / `machineId` / `sessionId` / `ideName` / `mode` …）。
- `machineId` / `sessionId` 用**由 uid 稳定派生**的值即可（同账号每次相同），保证指纹一致。

任务清单与进度查询：

```
GET https://www.workbuddy.cn/v2/activity/growth/tasks
→ data.tasks[]: { task_code, accept_status, progress:{current,target}, reward_credit, reward_energy, ... }
```

- 进阶任务**必须先接取**（`POST /activity/growth/tasks/accept`，body `{task_codes:[...]}`），不接取不计数。
- 🔴 接取接口**顶层 `code=0` 不代表逐条成功** —— 必须看 `data.results[].status === 'accepted'`。
- 达标后领奖：`POST /activity/growth/tasks/{task_code}/claim`。

| `task_code` | 关键 `eventCode` | 备注 |
|---|---|---|
| `create_canvas` | `agent_task_created`(task_mode=design) + `wbx_design_canvas_task_create` | |
| `playbook_prompt` | `playbook_prompt_send` | |
| `automation_1` | `agent_task_created`(task_mode=automation) + `automated_task_create_suc` + `automated_task_execute` | |
| `Library_read` | `web_element_click`(element_id=library_doc_intro_click) | |
| `Expert_lighthouse` | `expert_summoned` + `expert_actual_use` | 找名字含「轻量 / lighthouse」的专家 |

| `skill_1` | 真实装一个技能 + `skill_info` | |
| `RichMeow_Chat` | `desktop_chat_sequence` 六连（open_app → new_conversation → send_message → receive_response → conversation_end → close） | |
| `expert_5` | `expert_summoned` + `expert_actual_use` ×5 | 5 个不同专家 |
| **`Expert_team_use_3`** | **见第三节** | 必须真实团队对话 |

> **两种上报信封别混：**
> - Web 侧：直接发**数组** `[ {eventCode, ...}, ... ]`
> - 桌面侧（Buddy_App 等）：发 `{ common: {...}, events: [ {eventCode, ...}, ... ] }`

## 三、「召唤 3 次专家团」为什么最难

它是唯一一个**必须真的发起一次对话、且必须带上团队标识**的任务。

### 3.1 专家团从哪来

公开的市场配置（无需鉴权）：

```
https://acc-1258344699.cos.accelerate.myqcloud.com/workbuddy/expert-marketplace/expert_center.json
```

筛 `expertType === "team"`（或 `_meta.expertType === "team"`）。实测该表含 **429 个专家、53 个专家团**（如「腾讯云技术支持」「软件开发团队」「交易分析团队」…）。

### 3.2 完整调用序列

```jsonc
// ① 建会话
POST /console/webchat/conversations            → { conversationId }

// ② 真发一次对话（关键：带 _meta）
POST /console/chat/completions
{
  "messages": [{"role":"user","content":"你好，请简单介绍一下你们团队能帮我做什么"}],
  "model": "glm-5.2", "stream": true,
  "conversationId": "<上一步的 id>",
  "_meta": {
    "codebuddy.ai": {
      "growthEvent": "[{\"eventCode\":\"ExpertActualUse\",\"id\":\"<teamId>\",\"expertType\":\"team\",\"extra\":{\"name\":\"<团队名>\",\"expertType\":\"team\",\"cost\":8,...}}]",
      "promptRequestId": "<uuid>", "clientSendTime": <ms>,
      "userId": "<uid>", "mode": "craft", "model": "glm-5.2",
      "expertId": "<teamId>",
      "expert": {"id":"<teamId>","name":"<团队名>","profession":"","prompt":"你好，请简单介绍…"},
      "tags": ["expert:<teamId>"]
    }
  }
}

// ③ 再补一条常规埋点
POST /v2/report  [ { "eventCode":"expert_actual_use", "id":"<teamId>", "expertType":"team", "cost":8, "conversationId":"<id>", ... } ]
```

每轮之间 **sleep 5 秒**。

### 3.3 三个易错点

1. `growthEvent` 是**字符串**（里面是一个 JSON 数组），不是对象。
2. 里面的 `eventCode` 是 **`ExpertActualUse`（驼峰大写开头）**，与常规埋点 `expert_actual_use`（下划线小写）**不是同一个**，两个都要发。
3. **只发埋点不发起对话 = 进度纹丝不动。** 这是排查时最先要确认的一点。

## 四、加新任务的通用套路

1. `GET /v2/activity/growth/tasks` 看有没有新 `task_code`；
2. 在客户端（开 `--remote-debugging-port=9222`，走 CDP 抓 `Network`）**真实操作一遍**，抓出它上报了哪些 `eventCode` 与字段；
3. 照抄进 `growth-tasks.js`，在 `recipes` 数组里注册；
4. 本地跑一遍，再 `GET` 任务进度确认真的动了。

> 若任务需要"真实副作用"（如换主题、改系统设置），建议**默认跳过**，别为了积分把机器搞乱。
